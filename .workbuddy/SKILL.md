# 概念学习资料生成 Skill

把一个"我不懂的概念"变成一份**能自己复习、能拿来考自己、每个结论都能追到原始来源**的学习资料。

这个 Skill 不是给某三个概念写的提示词。它是一套**与概念无关的加工流程**：换任何一个新概念，走同一套步骤，产出一份结构相同的资料。

---

## 一、什么时候用 / 什么时候不用

**应该用：**
- 用户给出一个概念名词或短语，要求"学一下""讲清楚""整理成资料"。
- 用户在做阶段性的知识梳理，需要把零散理解沉淀成文件。
- 需要为一个已经"听过但说不清"的术语建立可复述的解释。

**不应该用：**
- 用户只是随口问一句定义，一句话就能答完，不需要产出文件 → 直接回答。
- 用户要的是操作手册 / 教程（"教我怎么装 X"），而不是概念理解 → 换用对应的流程型 Skill。
- 概念本身还没有稳定共识（纯观点、纯预测），无法找到可核查来源 → 停手，向用户说明并确认是否仍要生成（此时必须把资料标注为"观点性，无可核查来源"）。

---

## 二、输入信息

| 项 | 是否必需 | 缺失时的处理 |
|---|---|---|
| 概念名称（中文或英文） | 必需 | 追问用户，不要自行替换成"相邻的更热门的概念" |
| 用户当前的理解水平 / 困惑点 | 可选 | 默认按"知道基本名词但说不清机制"的读者来写 |
| 学习目的（考试 / 写作 / 工程使用） | 可选 | 默认"工程使用 + 能向别人解释" |
| 指定资料来源 | 可选 | 按第四节自己去检索并核实 |
| 输出文件名或存放目录 | 可选 | 默认 `learning-notes/<slug>.md` |

`slug` 规则：概念英文名小写、空格换成连字符（`Agent` → `agent`，`大模型的上下文` → `llm-context`）。若已存在同名文件，则**在原文件上追加"更新记录"并修订内容**，不要新建重复文件。

---

## 三、生成步骤

按顺序执行，不要跳步。

**第 0 步 · 先定位概念，再动手**
用一句话写清这个概念**解决什么问题**（它是因为什么痛点被提出来的）。如果一个概念找不到它的问题背景，说明还没理解，不要继续写。

**第 1 步 · 检索并锁定来源**
找 3–8 个来源。优先级：**同行评审论文（期刊/会议）** > 原始论文（arXiv 预印本）> 官方文档 / 官方工程博客 > 权威综述 > 二手解读（只能作为理解辅助，不能作为唯一依据）。
若该概念确实存在对应的学术文献，**学术来源至少 2 条**；如果这个概念本身就是行业约定（如某些平台专有名词），必须承认这一点，不要硬凑一篇论文来装点。

**第 2 步 · 核实来源真实可达，并核对元数据**

对每一条链接做一次可达性检查，把结果记进资料里：

```bash
curl -s -o /dev/null -w "%{http_code}  %{url_effective}\n" -L --max-time 25 \
  -A "Mozilla/5.0" "<URL>"
```

- 返回 `200` → 可用，记录访问日期。
- 返回 `403` / `000`（沙箱或网络限制）→ 用另一种方式复核（抓取工具读取页面正文），确认页面确实存在且内容与引用一致后，标注"经抓取核验，直连被网络策略拦截"。
- 内容与引用不符、或页面不存在 → **删掉这条来源**。绝不允许保留无法核实的链接。

**光打状态码不够，还要逐项核对元数据**（这一步最容易发现问题）：

- **论文**：标题、作者名单、v1 提交日期、最新版本日期、**Comments 字段里有没有写 camera-ready / accepted**、有没有指向期刊的 Related DOI。
- **文档**：确认它确实是官方域名，而不是转载页。

> ⚠️ **绝对不要凭记忆写 arXiv 编号。** 编号是纯数字，记错一位就会指向一篇完全不同的论文，而这种错误在打状态码时**完全看不出来**（页面照样返回 200）。必须通过检索确认编号后，再打开该编号的页面核对标题是否与你要引用的论文一致。本 Skill 的上一版就踩过这个坑。

**第 3 步 · 用自己的话写解释**
写"个人解释"时，禁止整段搬运原文或对话内容。做法是：
1. 读原始来源，合上；
2. 用一句大白话定义它；
3. 再写一个类比或反例；
4. 最后回头对照来源，检查有没有说错、说过头、漏掉前提。

**第 4 步 · 提取核心机制 / 组成**
把概念拆成 3–6 个可命名的部件或环节，每个部件写"它负责什么"。机制要能推出结论——如果只列名词而不解释因果关系，就是没写到位。

**第 5 步 · 画图**
见第五节的"可视化要求"。**图不是装饰**：画不出来通常说明机制还没拆清楚。先画主循环/主结构图，再画那张最能说明"量"的图。

**第 5 步 · 设计一个具体应用场景**
必须具体到可复述：什么人、面对什么输入、走哪几步、为什么这个场景**非它不可**（说明不用它会怎样）。禁止只写"常用于各种 AI 场景"这类空话。

**第 6 步 · 分离"易混问题"与"使用边界"**
- 易混问题：最容易和它混淆的 1–3 个概念，逐条写清"区别在哪一句判据上"。
- 使用边界：什么时候它不适用、代价是什么、失效模式是什么。

**第 7 步 · 出题，并强制按难度分档排序**
自测题 6–9 道，**必须分三档、按从易到难排列**，每档加 ★ 标注：

| 档位 | 考什么 | 典型问法 |
|---|---|---|
| ★ 基础档（2–3 道） | 概念记忆与辨析 | "这是什么""这两个怎么区分""判据是哪一句" |
| ★★ 应用档（2–3 道） | 机制推理 | "如果去掉某个部件会怎样""为什么会这样""用数据说明" |
| ★★★ 综合档（2–3 道） | 设计与迁移 | "换到新场景还成立吗""请设计一个方案/验证方案" |

硬性要求：
- **禁止把难题排在简单题前面**，也禁止三档混排。
- 每道题的参考答案紧接着题目写，且**答案必须能在正文中找到依据**（要能指回某一节）。
- 出完之后回头检查一遍：★★★ 档的题是否真的需要综合多处机制才能答，而不是把 ★ 档的题换个说法。

**第 8 步 · 落盘并更新索引**
写入 `learning-notes/<slug>.md`，并在 `learning-notes/INDEX.md` 中登记一行（概念 / 文件 / 生成日期 / 来源数 / 状态）。索引不存在则创建。

## 四、资料来源要求（硬性）

1. **不许编造。** 任何链接、标题、作者、日期、数字，都必须在真实页面上出现过。宁可少写一个来源，也不能凑数。
2. **优先一手来源。** 论文给 arXiv 编号或 DOI，官方文档给官方域名下的地址。二手解读（博客、公众号、聚合站）只能作为"辅助理解"，且必须明确标注它是二手。
3. **一条来源写三段信息**：出处（作者/机构 + 标题 + 年份）、链接、以及**它支撑了本文哪一句结论**。写了链接但说不出它支撑什么，就不该列进去。
4. **区分"来源说的"和"我认为的"。** 事实性陈述必须有来源；推论、类比属于个人解释，要能看出是解释。
5. **标注时效。** 记录访问日期。涉及"当前最好/最新版本"这类会过期的判断，必须写明时间点。
6. **无法核实的内容写进"存疑清单"**，不要伪装成已确认。
7. **学术来源优先，并标注评审状态。** 概念解释应尽量以同行评审文献（期刊 / 会议）为第一依据。每条学术来源必须标注「同行评审」或「预印本」，判定标准是：

   > **只有一手页面（通常是 arXiv 的 Comments 字段）明确写了 camera-ready / accepted，或给出了指向期刊的 Related DOI，才可标为「同行评审」；其余一律标「预印本」——即使它实际上已被会议接收。**

   这条规则会让表格看起来"保守"，但它换来的是**每个标记都能被读者自己复核到**。宁可保守，也不要留下一个自己核实不了的标记。同时必须在资料里写明这个判定标准，否则读者会误以为"预印本"等于"没发表过"。
8. **不要把行业文档包装成学术结论。** 官方文档、工程博客、行业标准属于"工程约定"，不是同行评审成果。输出结构里必须把这两类来源**分表列出**；正文中若用博客支撑某条论断，要写明它属于行业实践而非学术结论。

## 五、输出结构（固定模板，任何概念都填这一套）

```markdown
# <概念名称>

> 元信息：slug / 生成日期 / 所用 Skill 版本 / 资料状态（已核查 / 部分存疑）

## 1. 学习目标
3–4 条，用"能……"开头，可检验。（读完后我应该能做到什么）

## 2. 核心问题
3–5 个问题。回答完这些问题，就算学会了。

## 3. 一句话定义与个人解释
- 一句话定义：
- 大白话解释：（自己的话）
- 一个类比 / 一个反例：

## 4. 核心机制或组成
3–6 个部件，每个写"负责什么 + 为什么需要它"。
至少嵌入 1 张图解（建议编号为 4.0，先给全景）。
若该概念有学术对应，在此节或独立小节写一段"这个概念的学术位置"。

## 5. 一个具体应用场景
具体的人 + 具体的输入 + 具体步骤 + 为什么非它不可。
再补一句"上线前怎么验证"。

## 6. 容易混淆的问题
逐条列出与它最像的概念，写明"区别落在哪一句判据上"。

## 7. 使用边界与失效模式
什么情况下不该用它 / 代价是什么 / 会怎么失败。

## 8. 自测问题（按难度递进）
必须分 ★ / ★★ / ★★★ 三档并按从易到难排列，每档 2–3 道。
每道题后紧跟参考答案，答案要能指回正文某一节。

## 9. 参考来源
分两张表：
- 表 A 学术来源：出处 | 链接 | **评审状态** | 支撑本文哪一句结论
- 表 B 行业标准 / 官方文档：出处 | 链接 | 支撑本文哪一句结论
表后必须写明"评审状态的判定标准"，并统一标注访问日期与核查方式。

## 10. 存疑与待确认
无法核实的说法、二手来源、会过期的判断、本资料自己做的类比（要标明"这是我认为的"）。

## 11. 更新记录
YYYY-MM-DD：初次生成 / 修订了什么
```

第 9–11 节是**不可省略的自证结构**：没有来源、没有存疑标注、没有更新记录的资料，一律视为未完成。

### 可视化要求（硬性）

**至少 2 张图，且必须满足：**

1. **至少 1 张 Mermaid**：画主循环、结构分层或时序。用 `flowchart TB/LR`、`sequenceDiagram` 都可以。节点标签里有特殊字符时**统一加引号**（`S["文字<br/>换行"]`）。
2. **至少 1 张表达"量"的图**：表格、ASCII 柱状图、或 Mermaid `xychart`。用 ASCII 时把柱形放进代码块里，保证在任何渲染环境下都能看。
3. **每张图下面必须有一句"这张图的重点是什么"**，否则图就是装饰。
4. **不许画装饰性的图**：画不出来通常说明机制还没拆清楚，这是内容问题不是排版问题。
5. **示意图要标明**。凡是示意而非原始数值的图（例如 U 型曲线的形状），必须写上"示意，非原始数值"，避免读者把形状当成数据。
6. **Mermaid 语法自检**：`sequenceDiagram` 的 `participant ... as` 别名避免使用括号；星号、引号等容易触发解析问题的字符要处理干净。

- [ ] 应用场景里能回答"为什么不用更简单的方案"。
- [ ] 易混问题至少给出**一条可操作的判据**，而不是"前者更高级"这种空话。

- [ ] 所有 Mermaid 代码块都能通过语法检查（别名无括号、特殊字符已引号包裹）。
- [ ] **自测题严格按 ★ → ★★ → ★★★ 递进**，每档 2–3 道，没有把难题排在前面。
- [ ] ★★★ 档的题确实需要综合多处机制，而不是 ★ 档换了个说法。
- [ ] 所有链接都跑过可达性检查，并在文中标注访问日期。
- [ ] **每条学术来源都标了评审状态，且「同行评审」标记都能在一手页面复核到。**
- [ ] **arXiv 编号是检索确认过的**，不是凭记忆写的（打开编号页面核对过标题一致）。
- [ ] 学术来源与行业文档**分开列表**，没有把博客当学术结论。
- [ ] 若该概念属于行业约定、没有学术对应，已在正文里明确交代这一点。
- [ ] 每条来源都能对应到具体结论；对不上号的已删除。
- [ ] "个人解释"不是原文搬运：抽查任意一段，能在来源里找到对应内容，但表述不同。
- [ ] 自测题有答案，且答案能在正文中找到依据。
- [ ] 存疑内容没有混进正文当作事实；本资料自己做的类比已标明"这是我认为的"。
- [ ] `learning-notes/INDEX.md` 已登记或更新。
- [ ] 全文没有出现 API Key、密码、个人信息、内部链接。

## 七、典型调用

| 用户说法 | 本 Skill 的动作 |
|---|---|
| "帮我学一下 RAG" | 走第三节全流程，产出 `learning-notes/rag.md` |
| "把 MCP 整理成一份学习资料" | 同上，产出 `learning-notes/mcp.md` |
| "更新一下 agent 那篇，Anthropic 出了新文章" | 重跑第 1–2 步，修订原文件第 3–9 节，追加更新记录，不动文件名 |
| "我就想知道 Skill 是啥" | 不生成文件，直接口头解释一句，并问是否需要沉淀成资料 |

## 八、边界（这个 Skill 不做什么）

- 不代替用户做判断：它产出的是"有出处的学习材料"，不是"正确答案"。
- 不因为用户说"大概是这样"就写进正文；没有来源的一律进存疑清单。
- 不合并多个概念（那是 `concept-relationship.md` 的职责，属于单独的一次任务）。
- 不负责提交与推送；文件落盘后由用户确认再进入版本管理。
